## Context

仓库 `main` 当前只有提交 `f5b2238`，该提交包含 `build-local-campus-notice-inbox` 的提案、四项能力规格、技术设计和 55 项实施任务，并已与 `origin/main` 同步。现有 `.gitignore` 已排除基础依赖、构建产物、环境变量、本地数据库、备份和模型文件，但还没有提交前扫描、GitHub 检查、分支保护、版本标签规则或统一回退说明。

本变更是纯仓库治理，不改变应用规格。它需要同时服务人工开发和 OpenSpec apply 流程，并在 Windows PowerShell 环境可执行。

## Goals / Non-Goals

**Goals:**

- 让每个完成并验证的独立修改在 GitHub 上拥有可查询的 commit。
- 让每个可运行或可验收版本拥有唯一、不可移动的标签和变更记录。
- 在提交和合并前阻止通知数据、密钥、数据库、备份、模型二进制和常见凭据进入仓库。
- 提供无需改写共享历史的查询、比较、定位和回退流程。
- 将 Git 检查、提交和推送纳入 OpenSpec apply 的完成定义。

**Non-Goals:**

- 不为每次保存文件或未验证的中间状态制造提交。
- 不自动提交存在失败测试、敏感文件命中或无关用户修改的工作区。
- 不在本变更中改写既有 Git 历史或删除远程分支。
- 不把 Git 作为本地应用数据、通知截图或模型文件的备份系统。

## Decisions

### 1. 用原子 commit 和版本 tag 表达两种粒度

“修改”和“版本”使用不同对象表达：

- 一个完成并通过相关验证的 OpenSpec 任务或同一目的的最小修改，对应一个原子 commit。
- 一个可运行、可演示或可验收的里程碑，对应一个指向 `main` 精确 commit 的带注释 SemVer tag。
- 一个版本可以包含多个原子 commit，但每个版本至少有一个新 commit；不得用空提交伪造版本变化。

选择该方案而不是“每次保存都提交”，是因为后者会产生不可读的历史，也经常记录无法构建的状态。选择带注释 tag 而不是仅依赖分支名，是因为 tag 能稳定记录版本号、日期、摘要和目标 commit。

首版版本路线如下，后续只有范围变化时才调整：

| 标签 | 固定内容 | 进入条件 |
|---|---|---|
| `v0.1.0-plan.1` | 当前初版产品与技术方案，目标为 `f5b2238` | 已完成并严格校验 |
| `v0.1.0-plan.2` | 版本治理规则落地 | 本变更全部任务完成并验证 |
| `v0.2.0-alpha.1` | Windows 桌面壳、类型合同和加密数据基础 | 原方案任务组 1 至 3 通过 |
| `v0.3.0-alpha.1` | 文字/截图采集和本地理解闭环 | 原方案任务组 4 至 5 通过 |
| `v0.4.0-beta.1` | 任务核对、管理和本地提醒闭环 | 原方案任务组 6 至 7 通过 |
| `v0.5.0-beta.1` | 加密备份、恢复、删除及安全验证 | 原方案任务组 8 和相关安全验收通过 |

### 2. 每个 OpenSpec 变更使用独立分支，保留原子 commit 合入 main

分支命名为 `change/<change-name>`。apply 开始前必须：

1. 检查工作区和当前分支，读取 `origin/main`，记录起始 commit。
2. 从最新且干净的 `main` 创建或继续对应变更分支。
3. 每完成一个可独立验证的任务，更新任务状态、检查差异、运行相关测试和敏感扫描，然后创建一次 Conventional Commit。
4. 每个成功 commit 随即推送变更分支，使回退点同时存在于 GitHub。
5. 全部适用验证通过后通过 Pull Request 合入受保护的 `main`，保留原子 commit，不使用 squash 合并。

推荐提交格式为 `<type>(<scope>): <summary>`，正文记录 OpenSpec 变更名、任务编号和验证结果。允许的主要类型包括 `feat`、`fix`、`test`、`docs`、`refactor`、`build`、`ci` 和 `chore`。

相比直接在 `main` 连续提交，变更分支允许推送未完成但已验证的阶段性回退点，同时避免半成品进入发布主线。

### 3. 版本只在 main 验证后创建，标签不可复用

版本门禁要求：

- `main` 工作区和远程跟踪状态一致。
- 对应 OpenSpec 任务达到该里程碑定义，严格校验与相关自动化测试通过。
- 敏感数据扫描和大文件检查通过。
- `CHANGELOG.md` 记录用户可见变化、内部变化、已知限制和目标 commit。
- 使用 `git tag -a <version> -m <summary>` 创建标签，并显式推送该标签。

标签创建后不得移动、覆盖或复用。若版本有问题，创建修复 commit 和新版本标签；不修改旧标签指向。

### 4. 已发布历史只通过 revert 回退

查询和回退入口记录在 `VERSIONING.md`：

- 用提交图、OpenSpec 任务编号、文件历史和标签定位变化。
- 查看旧版本时使用 tag 或 commit 的只读检出，不移动 `main`。
- 撤销单个已推送修改时使用 `git revert <commit>`，验证后把 revert commit 推送到 GitHub。
- 撤销一组版本修改时按明确范围生成 revert commit，并创建新的补丁版本标签。
- `git reset --hard`、交互式 rebase、删除共享 tag 和强制推送不得用于已发布历史。

该策略会保留被撤销的提交，但它完整记录“做了什么、为什么撤销”，比重写历史更适合审计和恢复。

### 5. `.gitignore` 采用按数据类别分区的拒绝清单

在现有规则上补齐以下类别：

- 凭据和签名材料：`secrets/`、`.secrets/`、`*.pfx`、`*.p12`、`*.jks`、`*.keystore`、访问令牌配置和本地认证文件。
- 本地通知数据：应用数据目录、私有截图目录、剪贴板样本、真实通知夹具和导出内容。
- 数据库旁路文件：`*.db-journal`、`*.sqlite-*`、WAL、SHM 及数据库恢复点。
- 密钥与备份：DPAPI 包装密钥、keyring/keystore 目录、加密备份和恢复临时目录。
- 模型及推理缓存：GGUF、ONNX、ORT、safetensors、模型缓存和下载临时文件。
- 诊断数据：日志、崩溃转储、性能采样和可能包含正文的临时文件。

不能全局忽略 `*.png`、`*.json` 或所有测试数据，因为产品图标、公开合成夹具和结构化合同需要版本控制。可提交测试夹具必须位于明确的公开目录，并经过合成或脱敏审查。

### 6. `.gitignore`、本地 hook 和 GitHub CI 形成三层检查

`.gitignore` 只防止未跟踪文件被意外加入，不能阻止强制添加或清除已有历史，因此增加：

1. 仓库管理的 PowerShell 安全检查脚本，检查暂存文件名、扩展名、大小和常见秘密模式。
2. 仓库管理的 pre-commit hook，通过安装脚本设置 `core.hooksPath`，调用同一安全检查和 `git diff --cached --check`。
3. GitHub Actions 在 Pull Request 和 `main` 推送时扫描完整差异，复核秘密、大文件和被禁止路径。

本地 hook 可以被 `--no-verify` 绕过，因此 GitHub `main` 分支规则禁止强制推送和删除，并要求安全检查通过后才允许合并。任何工具都无法阻止有管理员权限的人故意绕过全部规则，但三层门禁可以阻止正常开发中的意外泄露。

### 7. 将流程写入项目指引和 OpenSpec apply 完成定义

实施时新增：

- `AGENTS.md`：规定自动化代理在修改前后执行的 Git 状态检查、提交粒度、测试、敏感扫描、推送和禁止行为。
- `CONTRIBUTING.md`：面向人工开发者描述分支、提交、PR 和敏感数据规则。
- `VERSIONING.md`：记录版本路线、查询命令、标签规则和回退流程。
- `CHANGELOG.md`：按版本记录变化和目标提交。
- `openspec/config.yaml` apply guidance：要求 apply 在每个原子任务后留下验证过的 commit，并报告 commit 哈希。

OpenSpec 任务文件仍是工作进度来源，Git commit 是代码状态来源，版本 tag 是发布状态来源；三者通过变更名和任务编号关联，不互相替代。

### 8. 敏感信息一旦进入历史，先止损再处理历史

若扫描发现未推送的敏感文件，取消暂存、加入忽略并清理本地副本即可。若真实凭据已经推送：

1. 立即轮换或吊销凭据，把仓库临时设为受限状态。
2. 记录泄露范围和涉及提交。
3. 普通内容删除使用新 commit；只有必须从全部历史清除时，另行获得用户明确批准后使用专用历史清理工具并协调强制推送。
4. 清理后再次扫描所有 refs，并通知所有克隆重新同步。

历史清理具有破坏性，不能由常规 apply 自动执行。

## Risks / Trade-offs

- [每个原子任务都提交会增加 commit 数量] → 使用一致的类型、scope 和任务编号，确保提交可独立理解和回退；不提交未验证的文件保存状态。
- [每个 commit 都推送会增加网络操作] → 只在验证成功后推送变更分支；网络暂不可用时保留本地 commit，并在恢复后按顺序推送和核验远程哈希。
- [忽略规则过宽会隐藏应提交的测试资产] → 只忽略明确的私有目录和高风险扩展，公开合成夹具使用独立目录并由检查脚本允许。
- [忽略规则不能保护已经跟踪的文件] → 实施时扫描索引和完整历史，提交前脚本检查暂存区，CI 复核远程差异。
- [本地 hook 可被绕过] → 使用 GitHub 必需检查和受保护的 `main` 作为最终门禁。
- [revert 可能产生冲突或不能直接恢复数据库格式] → 每次回退仍需运行对应测试；涉及数据迁移时按照应用设计中的数据库恢复点和兼容策略处理。
- [版本路线可能随产品范围调整] → 已发布标签保持不变，未来里程碑用新提案和新标签表达，不移动旧标签。

## Migration Plan

1. 扫描当前索引和全部 Git 历史，确认基线不存在敏感数据或超限二进制；若发现秘密，先停止后续步骤并执行凭据轮换流程。
2. 扩展 `.gitignore`，新增安全检查脚本、hook 安装器和 GitHub 工作流；用无害的模拟秘密文件验证三层检查会失败。
3. 新增项目指引、版本文档和变更记录，并把 OpenSpec apply guidance 接入 `openspec/config.yaml`。
4. 为提交 `f5b2238` 创建并推送 `v0.1.0-plan.1` 带注释标签，核验远程 tag 指向精确基线。
5. 为本治理变更创建分支、逐项实施并保留原子 commit；完成全部验证和合并后创建 `v0.1.0-plan.2`。
6. 在 GitHub 配置 `main` 分支规则，禁止强制推送和分支删除，要求安全检查通过。
7. 回滚治理变更时使用 revert commit 撤销相关文件；保留既有基线标签和提交，不重写历史。

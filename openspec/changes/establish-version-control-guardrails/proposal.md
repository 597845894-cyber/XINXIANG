## Why

校园信箱将处理通知截图、本地数据库、加密密钥和模型资源，开发过程中既需要防止敏感数据进入 GitHub，也需要让每个可验证版本都有明确的提交、标签和安全回退点。当前仓库只有一个初版规划提交，尚未形成可重复执行的版本治理规则。

## What Changes

- 将提交 `f5b2238` 及 `build-local-campus-notice-inbox` 规划制品明确为首版设计基线，记录其产品范围、架构和实施阶段。
- 建立基于 OpenSpec 变更分支、原子提交、验证门禁和 GitHub 推送的开发流程；每个完成并验证的独立修改至少对应一个可查询提交。
- 采用 Conventional Commits，并为每个可运行或可验收版本创建不可复用的带注释 SemVer 标签和变更记录。
- 建立查询与回退规则：发布后不得强制推送或重写共享历史，普通撤销通过 `git revert` 形成新的可审计提交，版本恢复以标签和提交哈希为依据。
- 扩展 `.gitignore`，覆盖环境变量、证书私钥、本地通知、截图、数据库及其旁路文件、加密备份、密钥材料、模型二进制、日志、崩溃转储和私有测试夹具。
- 增加提交前敏感文件检查和 GitHub 侧检查，阻止高风险文件名、常见凭据格式和超限模型文件进入提交。
- 把版本控制要求写入项目级开发指引和 OpenSpec apply 操作指引，使后续实现流程在修改前后都检查 Git 状态、运行验证、创建提交并记录回退点。

## Capabilities

### New Capabilities

无。本变更只涉及版本控制、仓库安全和开发流程，不新增用户可观察的应用能力。

### Modified Capabilities

无。

## Impact

- 影响仓库根目录的 `.gitignore`、项目开发指引、OpenSpec 操作配置、版本说明、提交检查脚本和 GitHub 工作流。
- 不修改校园信箱应用需求、数据模型、运行时行为或外部 API，因此 `.openspec.yaml` 使用 `skip_specs: true`。
- 后续每个 OpenSpec apply 修改将产生更细粒度但有语义的提交；版本标签只在对应验收通过后创建和推送。
- 已经进入 Git 历史的秘密不能靠 `.gitignore` 清除，因此实施阶段必须先扫描完整历史；若发现真实凭据，先轮换凭据，再另行批准历史清理。

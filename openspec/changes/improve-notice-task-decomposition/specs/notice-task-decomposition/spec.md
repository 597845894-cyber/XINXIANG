## Purpose

为文字校园通知提供可核对的动作级任务拆分，完整保留并列事项、条件步骤、准备依赖和原文证据，同时避免把背景说明或结果影响误当成学生任务。

## ADDED Requirements

### Requirement: 按可执行动作拆分通知
系统 MUST 将通知中的每个独立、可执行的动作识别为一个候选任务；编号列表、并列要求、材料准备步骤和条件动作 MUST 被逐项覆盖。背景介绍、礼貌用语、提醒语、成绩影响说明和纯结果描述 MUST NOT 单独生成任务。

#### Scenario: 实习通知完整拆分（由后续聚合变更取代）
- **WHEN** 用户导入包含校友邦任务、纸质材料提交、实习手册、导师评语、单位盖章、拍照插入和档案袋装入要求的通知
- **THEN** 本旧变更不再作为生效验收标准；由 `simplify-notice-task-titles` 统一验收为两个主要候选，准备动作保留在详情和证据中。

#### Scenario: 背景句不生成任务
- **WHEN** 通知包含“实习即将结束”“请认真对待”或“以免影响成绩”等说明
- **THEN** 系统不为这些句子单独创建任务，但可以将其保留为通知摘要或候选的说明字段

### Requirement: 保留任务层级与依赖
每个候选任务 MUST 具有稳定标识，并可声明父任务、前置任务或条件关系。用户 MUST 能区分总任务与准备步骤；确认父任务不得自动确认未被用户确认的子步骤。

#### Scenario: 材料提交依赖准备步骤
- **WHEN** 通知要求在上课前提交纸质材料，并列出手册导出、鉴定表盖章和档案袋装入等准备工作
- **THEN** 系统将纸质材料提交作为父任务或汇总任务，并将相关准备动作关联为子步骤或前置依赖

#### Scenario: 分别确认候选
- **WHEN** 用户只确认“导出实习手册”而未确认“提交纸质材料”
- **THEN** 系统只创建前者对应的正式任务，后者继续保留在待确认候选中

### Requirement: 每项候选绑定原文证据
每个候选任务 MUST 至少绑定一个连续的原文证据片段或可验证范围；证据不足、证据与动作不一致或候选由模型推测产生时 MUST 标记为低可信或待确认。

#### Scenario: 证据缺失
- **WHEN** 模型输出一个无法在通知中定位的任务标题或字段
- **THEN** 系统拒绝该候选进入可快速确认列表，并提示用户编辑、删除或人工创建

### Requirement: 分析结果不得绕过人工确认
分析产生的候选任务 MUST 保持草稿状态，直到用户逐项确认、修改或删除；分析失败、校验失败、取消和回退 MUST 保留原文且不得写入半成品正式任务。

#### Scenario: 低可信候选需要核对
- **WHEN** 候选缺少截止时间、包含冲突字段或来自规则回退
- **THEN** 系统突出显示待确认原因，并阻止无提示的一键全部确认
